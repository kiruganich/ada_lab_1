# Проектирование словаря на B-дереве

Здесь разобраны требования присланного условия и решения, которые нужно принять до реализации. Алгоритмы дерева находятся в [конспекте B-дерева](BTREE_GUIDE.md), проверка качества — в [плане тестирования и отчёта](TESTING_AND_REPORT.md).

## 1. Контракт программы

Ввод обрабатывается до EOF. Успешная команда или обычный результат словарной операции выводит ровно одну строку.

| Команда | Результат |
| --- | --- |
| `+ word number` | `OK`, если добавлено; `Exist`, если нормализованный ключ уже есть |
| `- word` | `OK`, если удалено; `NoSuchWord`, если ключа нет |
| `word` | `OK: number` или `NoSuchWord` |
| `! Save path` | `OK` после успешного сохранения; иначе `ERROR: ...` |
| `! Load path` | `OK` после успешной замены словаря; иначе `ERROR: ...` с сохранением рабочего словаря |

Ключ — непустое слово из английских букв, длина от 1 до 256. Различия регистра не учитываются. Несколько разных ключей могут иметь одинаковые значения. Числа лежат в диапазоне `0 .. 2^64 - 1`.

При повторной вставке значение **не обновляется**:

```text
+ Apple 10  -> OK
+ APPLE 20  -> Exist
apple       -> OK: 10
```

Время по условию — 15 секунд, память — 512 МБ. Верхняя граница числа записей в присланном тексте не дана, поэтому обещать прохождение только по выбранному `t` нельзя: нужны замеры на больших наборах.

В предоставленных требованиях нет запрета на `std::string`, `std::vector` и умные указатели. Их можно рассматривать как средства хранения. Сам словарь должен реализовываться B-деревом; готовый `std::map` полезен как эталон в тестах.

## 2. Нормализация и сравнение ключей

Удобно преобразовывать буквы `A..Z` в `a..z` один раз при обработке команды. В дереве хранить только нормализованные слова. То же правило действует для загружаемых данных.

Тогда обычное лексикографическое сравнение строк задаёт нужный порядок:

```text
app < apple < banana
```

Если одна строка — префикс другой, более короткая меньше. Значения при выборе позиции не сравниваются.

Преобразование регистра относится только к словам. Имена операций `Save`, `Load` и путь к файлу нельзя автоматически приводить к нижнему регистру: на некоторых файловых системах регистр пути существенен.

Для заданного алфавита достаточно явного преобразования `A..Z`. Если использовать `std::tolower`, аргумент нужно сначала привести к `unsigned char`, а результат при необходимости — к `char`: передача отрицательного `char`, отличного от EOF, недопустима.

## 3. Представление значения

Максимум равен `18446744073709551615`. Для него подходит `std::uint64_t` из `<cstdint>` на целевой платформе с таким типом. Знакового `long long` недостаточно: его обычный максимум — `2^63 - 1`.

Не читать сначала в знаковый тип с последующим приведением. Не использовать значение 0 как признак отсутствия: 0 — допустимое значение словаря. Для результата поиска подходят `std::optional<uint64_t>` или `bool` вместе с выходным параметром.

Для корректного ввода из условия достаточно чтения беззнакового 64-битного значения. Если дополнительно проверять произвольный ввод, нужно явно отвергать минус, переполнение и лишние символы. Такие возможности не следует путать с обязательной обработкой повреждённых файлов: она требуется условием непосредственно.

## 4. Разделение ответственности

Удобная структура будущего проекта:

```text
include/btree.hpp     публичный интерфейс дерева
src/btree.cpp         поиск, вставка, удаление, владение узлами
src/persistence.cpp   двоичный формат и файловые операции
src/main.cpp          команды, нормализация, ответы и диагностика
tests/                эталонные, случайные и файловые проверки
bench/                генераторы нагрузок и сценарии измерений
docs/                 теория и материалы для отчёта
```

Это предложение организации, а не дополнительное требование контеста. Если система принимает только один исходный файл, нужно обеспечить подходящую сборку или объединение файлов, сохранив разделение ответственности в проекте.

Пример смыслового интерфейса:

```text
find(key) -> found(value) / not_found
insert(key, value) -> inserted / exists
erase(key) -> erased / not_found
clear()
save(path)
load(path)
```

Библиотека возвращает результаты операций и сообщает об ошибках. Печать `OK`, `Exist`, `NoSuchWord` относится к оболочке программы. Так дерево можно тестировать и измерять без текстового ввода-вывода.

Системные сбои нельзя маскировать под обычные результаты. Неудача выделения памяти при вставке — это `ERROR: Out of memory`, а не `Exist`.

## 5. Записи, узлы и владение памятью

Запись должна объединять слово и число:

```text
Entry:
    key: string
    value: uint64_t

Node:
    entries: упорядоченные записи
    children: владельцы дочерних узлов
    leaf: признак листа или свойство отсутствия детей
```

Параллельные массивы слов и чисел возможны, но требуют синхронных перемещений. Единый `Entry` снижает риск переставить слова и забыть их значения.

Для массивов фиксированной вместимости узлу нужны до `2t - 1` записей и `2t` детей. Для `std::vector` логическая длина меняется по фактическому числу элементов. Если отдельно хранить `count`, он должен точно совпадать с используемой длиной; лишний дублируемый счётчик создаёт ещё один инвариант.

У каждого узла ровно один владелец. Корень принадлежит дереву, дети — своим родителям. При слиянии и разделении передаётся владение, а не создаются два владельца одного адреса.

`std::unique_ptr<Node>` помогает автоматически освобождать поддеревья при выходе из функции и исключениях. Если используются сырые указатели, нужны явное уничтожение дерева и обработка всех промежуточных состояний. Поверхностное копирование объекта-владельца указателей недопустимо: оно приводит к двойному освобождению. Копирование нужно запретить или реализовать как глубокое; перемещение можно поддержать отдельно.

При `vector::insert`, `erase`, `resize` и перераспределении памяти могут стать недействительными ссылки и итераторы. После перестройки лучше заново получать нужный элемент по индексу. Нельзя сохранять ссылку на запись, удалить её контейнерной операцией, а затем использовать ссылку.

Слова длиной 256 можно хранить в `std::string` или в собственном буфере. Для C-строки из 256 букв нужен массив на 257 байт с завершающим нулём. Запас под максимум в каждой записи прост, но расходует память даже для слов из одной буквы.

Предварительное `reserve` до максимальной вместимости узла уменьшает число перераспределений при перестройках. Для листа резервировать массив детей необязательно. Слишком большие резервирования в каждом узле могут ухудшить расход памяти — это проверяется измерениями.

## 6. Исключения во время изменений

Одного `catch (bad_alloc)` в `main` недостаточно: исключение может произойти после частичной перестройки.

Пример опасной последовательности: удалить средний ключ из полного ребёнка, затем попытаться выделить правую половину. Если выделение не удалось, ключ уже потерян.

Правильный принцип для `splitChild`: сначала подготовить новые ресурсы и необходимые ёмкости, затем выполнять изменения, которые не требуют новых выделений и для выбранных типов гарантированно не бросают исключений. Копирование `std::string` тоже может выделять память; его нельзя считать безусловно безопасным.

Для первой реализации полезно добиться следующего:

- дерево и владельцы памяти остаются корректными после ошибки;
- записи не теряются из-за незавершённого разделения;
- новое слово появляется только после завершения вставки;
- удаление не начинает менять родителя до подготовки потенциально бросающих действий;
- временные объекты автоматически очищаются.

Условие явно требует неизменности рабочего словаря при ошибочном `Load`. Для остальных операций сохранение прежнего набора записей при отказе — полезная проектная гарантия, которую нужно обеспечить, а не просто приписать наличию `try/catch`.

Не нужно копировать всё дерево для каждой вставки: это превратит логарифмическую операцию в линейную. Лучше организовать подготовку и передачу владения локально.

## 7. Что означает двоичное сохранение

Нужно сохранить данные, по которым можно восстановить словарь в другом запуске процесса. Адреса узлов не имеют смысла после завершения программы.

Нельзя записывать `sizeof(Node)` сырых байтов узла, содержащего указатели, `std::string` или `std::vector`. Там находятся внутренние адреса, ёмкости и платформенные детали. Записывать нужно явно определённые поля формата.

И целые числа лучше кодировать явно: фиксированное число байтов и оговорённый порядок байтов, например little endian. Это делает формат независимым от расположения полей структуры и её выравнивания.

Условие не требует сохранить исходную форму дерева. Возможны два основных подхода.

| Подход | Что записывается | Восстановление |
| --- | --- | --- |
| Упорядоченные записи | Все пары по возрастанию ключа | Проверить записи и вставить в новое B-дерево |
| Структура дерева | Признак листа, число записей, записи и рекурсивно дети | Воссоздать узлы и проверить все инварианты |

Упорядоченные записи дают простой компактный формат и не зависят от `t`. Обычная последовательная вставка при загрузке требует `O(n log n)` времени при фиксированной степени и ограниченной длине слов. Линейное массовое построение возможно, но это отдельный алгоритм; сам по себе отсортированный файл его не обеспечивает.

Сохранение структуры позволяет читать дерево за линейное время по объёму файла и числу записей. Проверять нужно больше: заполнение, порядок, интервалы поддеревьев, число детей и одинаковую глубину листьев. Степень нужно хранить в заголовке или фиксировать как часть версии формата.

Для начала удобно выбрать формат упорядоченных записей. Если измерения покажут, что время `Load` существенно, можно обоснованно перейти к сохранению структуры либо к массовому построению.

## 8. Пример конкретного формата

Это проектный вариант для формата упорядоченных записей, а не формат, заданный преподавателем.

```text
8 байт      ASCII-сигнатура ADALBTR1
8 байт      N — число записей, unsigned little endian

Затем N записей:
2 байта     длина слова, unsigned little endian, 1..256
len байт    слово в нижнем регистре, без завершающего нуля
8 байт      значение, unsigned little endian

После последней записи — конец файла.
```

Последняя цифра сигнатуры обозначает версию. При несовместимом изменении формата меняется версия. В заголовке `N = 0` соответствует сохранённому пустому словарю; отдельно по условию принимается файл вообще без байтов.

**Длину нельзя непосредственно хранить в uint8_t:** число 256 в него не помещается. Два байта решают проблему без специального кодирования.

Размер файла:

```text
S = 16 + sum(2 + len_i + 8)
  = 16 + 10N + sum(len_i).
```

Для N слов длиной 10 это `16 + 20N` байт. Свободные слоты узлов, адреса и неиспользуемая часть строк не записываются.

Читать нужно с проверкой точного количества байтов. Сигнатура правильная, но до конца значения осталось только 3 байта — это повреждённый файл, а не «почти прочитанная» запись.

Проверки для непустого файла:

1. Сигнатура и версия распознаются.
2. Заголовок прочитан целиком.
3. Длины находятся в `1..256`, слова состоят только из `a..z`.
4. Значения прочитаны целиком как 64-битные беззнаковые числа.
5. Записи строго возрастают: нет дубликатов и нарушения порядка.
6. Прочитано ровно `N` записей, после них нет лишних байтов.
7. Не выполняются огромные выделения только потому, что заголовок объявил большое `N`.

Для обычного файла с известным размером полезна ранняя проверка: одной непустой записи нужно хотя бы 11 байт, поэтому `N <= remaining_bytes / 11`. Проверка через деление избегает переполнения произведения `11 * N`. Даже после неё каждое чтение всё равно проверяется.

Повреждение значения может превратить одно допустимое число в другое допустимое. Проверки структуры формата этого не заметят. Контрольная сумма позволяет обнаруживать многие такие повреждения; она может быть дополнительным полем следующей версии. Требование отвергать несовместимый формат не означает математически возможного обнаружения любой порчи без избыточности.

## 9. Безопасная загрузка

Рабочее дерево нельзя очищать до чтения и проверки файла.

```text
load(path):
    создать пустое временное дерево temp
    открыть файл

    если установлено, что файл отсутствует:
        заменить current на пустое temp
        успех

    если открыть не удалось по другой причине:
        ошибка

    если файл имеет длину 0:
        заменить current на пустое temp
        успех

    прочитать и проверить заголовок
    прочитать все записи в temp
    проверить конец файла и отсутствие ошибки чтения
    обменять current и temp без исключений
    успех
```

После успешного обмена временный объект владеет прежним деревом и освобождает его. При любой ошибке до обмена освобождается только временное дерево; рабочий словарь сохраняется.

Пик RAM при таком `Load` включает одновременно старый и новый словарь, а также буферы. Он может быть существенно выше обычного размера одного дерева. Не стоит дополнительно читать весь файл в большой массив, если данные можно проверять последовательно.

| Ситуация | Ответ | Состояние после команды |
| --- | --- | --- |
| Корректный файл с записями | `OK` | Только загруженные записи |
| Корректный файл с N = 0 | `OK` | Пустой словарь |
| Файл длиной 0 | `OK` | Пустой словарь |
| Установлено отсутствие файла | `OK` | Пустой словарь |
| Нет доступа к существующему файлу | `ERROR: ...` | Прежний словарь |
| Неверная сигнатура или версия | `ERROR: ...` | Прежний словарь |
| Усечённый непустой файл | `ERROR: ...` | Прежний словарь |
| Недопустимые длины, ключи, порядок | `ERROR: ...` | Прежний словарь |
| Ошибка чтения или нехватка памяти | `ERROR: ...` | Прежний словарь |

Неудачное открытие `ifstream` само по себе не доказывает отсутствие файла. Ошибки доступа, неверный тип пути и реальные ошибки I/O нужно отличать от отсутствия. Диагностика должна опираться на актуальный код ошибки операции или корректную проверку файловой системы с обработкой её ошибок. Не использовать случайно оставшееся старое значение `errno` как доказательство причины отказа.

## 10. Сохранение

`Save` не меняет рабочий словарь. Записи обходятся в порядке возрастания и кодируются выбранным форматом.

Для внутреннего узла с `m` ключами симметричный обход имеет вид:

```text
child[0], entry[0], child[1], entry[1], ..., entry[m-1], child[m].
```

Время сохранения — `O(S + n)`, где `S` — объём записанных байтов. При ограниченной длине слов это `O(n)`. На практике важны буферизация и скорость файловой системы.

Проверять нужно не только открытие, но и запись, сброс буфера и закрытие: ошибка, например при заполнении диска, может проявиться позже. `OK` выводится после успешного завершения всех нужных действий.

Для более надёжного сохранения можно писать во временный файл в том же каталоге, закрыть и проверить его, затем заменить целевой файл. Детали замены зависят от платформы. Это улучшает сохранность предыдущего файла; условие явно требует сохранности рабочего словаря при `Load`, но не задаёт такую файловую транзакцию для `Save`.

`flush` и успешное закрытие проверяют завершение записи на уровне обычного файлового API; гарантия переживания внезапного отключения питания потребовала бы дополнительных платформенных действий и в условии не оговорена.

## 11. Командный цикл и диагностика

Обрабатывать команды до конца ввода. Можно разбирать каждую строку отдельно: это удобно для границ команд и позволяет не потерять синхронизацию после ошибки. Для больших тестов нужно учитывать стоимость парсинга; использовать быстрый ввод и вывод без принудительного сброса после каждой строки.

Пути в примерах не содержат пробелов. Если поддерживаются пробелы в пути, нужно заранее определить правило чтения остатка строки. Не надо придумывать несовместимое расширение синтаксиса там, где контест ожидает обычный путь-токен.

Все штатные ответы и `ERROR: ...` выводятся в stdout согласно условию. Отладочные деревья, счётчики и собственные измерения туда попадать не должны; для них подходят отдельный режим, stderr или отдельный исполняемый файл.

Полезные английские сообщения:

```text
ERROR: Out of memory
ERROR: Cannot open file for writing
ERROR: Cannot read file
ERROR: Invalid file format
ERROR: Unsupported file version
```

Точный текст после `ERROR:` условие не фиксирует, но он должен быть на английском. Строку из локализованного системного сообщения нельзя без проверки считать английской диагностикой.

Границы обработки ошибок должны включать выделения в нормализации, подготовке записи и файловом чтении. Если чтение очередной строки находится вне `try`, ошибка выделения памяти при самом чтении не будет поймана обработчиком только тела команды. При этом ошибка вывода самой диагностики может физически помешать её показать; `catch` не даёт абсолютной гарантии работы при любом отказе среды.
