# Проверка словаря и подготовка отчёта

Материал относится к двум присланным заданиям: реализации словаря на B-дереве и исследованию скорости/памяти для «G. Отчёт + качество программ».

Для G требуются дневник работы, выводы о недочётах, сравнение исправленной программы с предыдущей версией и общие выводы. В условии названы gprof и dmalloc, при этом прямо разрешены аналогичные или более развитые средства. Практический набор для C++: gprof для профиля функций, Valgrind Memcheck для ошибок памяти, Massif для динамики использования кучи и обычный замер времени/пиковой памяти процесса. Санитайзеры полезны дополнительно.

Далее приведён план будущих проверок. Команды сборки — примеры для Bash в Linux/WSL после появления исходников; они не являются результатами уже выполненных измерений.

## 1. Минимальный пример протокола

Ввод:

```text
+ Apple 0
+ APPLE 7
aPpLe
+ banana 18446744073709551615
! Save sample.dict
- apple
apple
! Load sample.dict
apple
banana
- BANANA
banana
```

Ожидаемый вывод при успешных файловых операциях:

```text
OK
Exist
OK: 0
OK
OK
OK
NoSuchWord
OK
OK: 0
OK: 18446744073709551615
OK
NoSuchWord
```

Этот пример проверяет регистр, сохранение старого значения при дубликате, крайние числа, удаление и восстановление. Он не покрывает все перестройки дерева.

## 2. Проверки операций дерева

| Проверка | Что должна обнаружить |
| --- | --- |
| Поиск и удаление в пустом дереве | Неверную обработку пустого корня |
| Вставка и удаление единственного ключа | Ошибки перехода к пустому словарю |
| Повторная вставка с другим значением | Неправильное обновление существующей записи |
| Один ключ в разных регистрах | Отсутствующую или непоследовательную нормализацию |
| Разные ключи с одинаковыми значениями | Ошибочное требование уникальности значений |
| Слова длиной 1, 255 и 256 | Ошибки границ буферов и кодирования длины |
| `a`, `aa`, `aaa`, `ab` | Ошибки сравнения префиксов |
| Длинный общий префикс и разная последняя буква | Границы строк и стоимость сравнений |
| Значения 0, `2^63`, `2^64 - 1` | Использование знакового типа или специального «нулевого» маркера |
| Вставки по возрастанию и убыванию | Разделения на краях узлов, несколько уровней |
| Удаления по возрастанию и убыванию | Крайние дети, слияния, сокращение корня |
| Многократные вставка/удаление одного слова | Ошибки повторного владения памятью |
| Удаление отсутствующего слова из большого дерева | Ошибки результата и сохранения набора пар |

При тестировании сначала взять `t = 2`, затем повторить проверки с несколькими степенями. Для счётчика числа записей важны дубликаты и отсутствующие удаления: они не должны менять размер словаря.

Для проверки конкретных ветвей удобно записывать в отдельном тестовом режиме счётчики вызовов `split`, заимствований с каждой стороны, слияний, замены предшественником/преемником и сокращения корня. Случайный тест без этих сведений может ни разу не выполнить нужный случай.

## 3. Проверка инвариантов

После каждой завершённой операции в отладочных тестах рекурсивно проверять:

1. Слова нормализованы, ключи внутри узла строго возрастают.
2. Некорневой узел содержит `t - 1 .. 2t - 1` записей; корень соответствует исключениям.
3. Лист не имеет детей; внутренний узел с `m` записями имеет ровно `m + 1` детей.
4. Все ключи поддерева лежат в переданных строгих нижней и верхней границах.
5. Все листья имеют одинаковую глубину.
6. Количество записей при обходе равно счётчику размера, если такой счётчик хранится.
7. Симметричный обход даёт строго возрастающие ключи и правильные значения.

Проверки только соседних ключей в каждом узле недостаточно: ребёнок может содержать слово из неправильного диапазона. Например, локально отсортированный левый ребёнок `[5, 15]` у корня `[10]` всё равно некорректен.

Полная проверка инвариантов после каждой команды стоит линейно по дереву. Использовать её в тестах, а не включать безусловно в рабочую сборку для контеста или замера скорости.

## 4. Сравнение с эталоном

Для тестов подойдёт `std::map<std::string, uint64_t>` с той же нормализацией. В готовой программе он не заменяет B-дерево.

Генерировать воспроизводимые последовательности команд с фиксированным seed:

- новые и повторные вставки;
- успешные и неуспешные поиски;
- успешные и неуспешные удаления;
- смешанный регистр;
- значения из полного допустимого диапазона;
- слова разной длины, включая общие префиксы;
- периодические сохранения, изменения и загрузки снимков.

Сравнивать не только финальное содержимое, но и ответ каждой операции. После ошибки печатать seed, номер операции и минимальный воспроизводимый префикс команд. Отдельно запускать валидатор инвариантов: совпавшие ответы ещё не доказывают сохранение заполнения и баланса.

Генератор слов должен выдавать английские буквы. Строки вида `word123` не соответствуют алфавиту задачи. Номер можно кодировать буквами либо генерировать случайные слова с контролем дубликатов.

Для простого случайного выбора одинаковых типов операций нужно следить за фактической нагрузкой: если почти все удаления промахиваются, такой тест плохо проверяет удаление из существующего дерева.

## 5. Проверки Save и Load

Обязательные сценарии:

1. Пустой словарь → Save → Load.
2. Непустой словарь → Save → полное изменение словаря → Load → восстановление снимка.
3. В рабочем словаре есть посторонний ключ: успешный Load должен его удалить, а не объединить наборы.
4. Load файла длиной 0 возвращает `OK` и очищает прежний словарь.
5. Load заведомо отсутствующего файла возвращает `OK` и очищает прежний словарь.
6. Нет прав чтения существующего файла: ошибка, старые данные остаются.
7. Нет прав записи или невозможно создать файл: `ERROR: ...` при Save.
8. Повреждённый непустой файл: `ERROR: ...`, словарь остаётся прежним.
9. Повторные циклы Load/Save не приводят к росту числа живых узлов и утечкам.

Отсутствующий файл нужно действительно удалить или выбрать гарантированно отсутствующий путь перед проверкой. Путь, который существует, но недоступен, проверяет другую ветвь.

Для проверки повреждений выбранного формата:

- изменить сигнатуру и версию;
- обрезать корректный файл на разных позициях, включая внутри заголовка и значения;
- записать длину 0 или больше 256;
- подставить недопустимый символ;
- нарушить порядок записей или сделать дубликат;
- увеличить объявленное число записей;
- дописать лишние байты после конца данных;
- подать случайные непустые байты.

**Исключение:** обрезание до нулевой длины должно давать успешную загрузку пустого словаря по условию. Любой другой обрезанный префикс не следует автоматически считать пустым файлом.

После каждой ожидаемой ошибки проверять несколько старых ключей и отсутствие ключей из незавершённой загрузки. Сам факт вывода `ERROR:` ещё не доказывает сохранность состояния.

Если формат хранит структуру дерева, дополнительно повреждать число ключей/детей, интервалы поддеревьев и глубины листьев. Для слишком глубокой структуры нужны ограничения, вытекающие из допустимого дерева/числа записей, чтобы повреждённый файл не приводил к неограниченной рекурсии.

## 6. Ошибки памяти

Для быстрой отладки можно собрать отдельную версию с AddressSanitizer и UndefinedBehaviorSanitizer:

```bash
g++ -std=c++17 -O1 -g -fno-omit-frame-pointer \
    -fsanitize=address,undefined -Iinclude src/*.cpp -o dictionary_asan
./dictionary_asan < tests/workload.txt > /dev/null
```

Эти параметры добавляют проверки обращений к памяти и ряда случаев неопределённого поведения; детали и поддержка зависят от компилятора и платформы. [Документация GCC](https://gcc.gnu.org/onlinedocs/gcc/Instrumentation-Options.html).

Для Valgrind собрать отдельный бинарный файл без ASan:

```bash
g++ -std=c++17 -Og -g -Iinclude src/*.cpp -o dictionary_debug
valgrind --tool=memcheck --leak-check=full --show-leak-kinds=all \
    --track-origins=yes --error-exitcode=1 \
    ./dictionary_debug < tests/workload.txt > /dev/null
```

Memcheck выявляет, в частности, недопустимые чтения/записи, использование освобождённой памяти, некоторые обращения к неинициализированным значениям, неверное освобождение и утечки. Время работы под ним не является скоростью обычной программы. [Документация Memcheck](https://valgrind.org/docs/manual/mc-manual.html).

Нагрузки должны включать не только вставки, но и слияния, очистку, замену корня, успешные и неуспешные загрузки. Особенно важно освобождение частично построенного временного дерева при ошибке чтения.

Отчёт анализировать по содержанию: `definitely lost`, `indirectly lost`, `possibly lost` и `still reachable` имеют разные значения. Наличие достижимых блоков стандартной библиотеки само по себе не равно доказанной утечке узлов. В то же время оставлять собственное дерево неосвобождённым только потому, что память вернёт ОС, для этой ЛР не следует.

Если выбран dmalloc, нужно изучить его C++-интеграцию: перехват `new`/`delete` не сводится к механическому копированию примера с `malloc` из условия. [Документация dmalloc](https://dmalloc.com/docs/dmalloc.html) описывает специальную библиотеку для C++.

Отдельно можно внедрять контролируемый отказ выделения памяти в тестовой сборке: отказ на первом, втором и следующих выделениях. Цель — проверить сохранность дерева и очистку промежуточных объектов, а не просто достижение блока `catch`.

## 7. Профиль времени с gprof

Нужна отдельная сборка: `-pg` должен присутствовать и при компиляции, и при линковке. При одной команде это выглядит так:

```bash
g++ -std=c++17 -O2 -g -pg -Iinclude src/*.cpp -o dictionary_prof
./dictionary_prof < tests/workload.txt > /dev/null
gprof ./dictionary_prof gmon.out > gprof.txt
```

При нормальном завершении программа записывает `gmon.out`. Профиль относится к выполненному сценарию: если в нём не было удалений или загрузок, их стоимость не исследована. [Компиляция с gprof](https://sourceware.org/binutils/docs/gprof/Compiling.html), [запуск и файл профиля](https://sourceware.org/binutils/docs/gprof/Executing.html).

В профиле смотреть собственное время функций, время с учётом вызовов и число вызовов. Возможные дорогие места: строковые сравнения, копирование записей, выделения узлов, перемещения внутри узлов, разбор команд, файловое чтение и запись. Это гипотезы для проверки, а не заранее найденные недостатки.

Очень короткий запуск может дать мало отсчётов. Нужна достаточно длительная воспроизводимая нагрузка. Оптимизация и встраивание функций меняют вид профиля, поэтому фиксировать параметры сборки. Профилируемая сборка сама добавляет накладные расходы.

## 8. Время и объём памяти

Для скорости нужна обычная оптимизированная сборка без gprof, Valgrind и санитайзеров:

```bash
g++ -std=c++17 -O2 -DNDEBUG -Iinclude src/*.cpp -o dictionary
/usr/bin/time -v ./dictionary < tests/workload.txt > /dev/null
```

Зафиксировать elapsed time, CPU time и maximum resident set size. RSS включает память процесса, а не только узлы дерева; это отличается от суммы размеров записей и от профиля кучи. Названия полей и единицы следует указать по выводу установленного инструмента.

Для исследования динамики кучи:

```bash
valgrind --tool=massif --massif-out-file=massif.out \
    ./dictionary_debug < tests/workload.txt > /dev/null
ms_print massif.out > massif.txt
```

Massif показывает использование кучи и места выделений; учёт стеков по умолчанию не включён. Проверка утечек, пик RSS и профиль кучи отвечают на разные вопросы. [Документация Massif](https://valgrind.org/docs/manual/ms-manual.html).

Для отдельного измерения алгоритма вызывать библиотеку напрямую на заранее подготовленных операциях. Для измерения программы целиком включать парсинг и вывод. Перенаправление в `/dev/null` убирает вывод в терминал, но не стоимость форматирования ответов.

В своих измерениях интервалов C++ предпочтителен монотонный `std::chrono::steady_clock`. В семинарском примере `seminars/1sem/.cpp` используется `system_clock`; системное время может корректироваться и для измерения длительностей менее удобно.

## 9. Нагрузки и честное сравнение

Использовать несколько размеров данных и сценариев:

| Сценарий | Что исследуется |
| --- | --- |
| Только уникальные вставки | Создание узлов, разделения, рост памяти |
| Поиск существующих и отсутствующих слов | Строковые сравнения и спуски |
| Только успешные удаления | Заимствования, слияния и освобождение |
| Смесь команд с заданными долями | Типичная динамическая работа словаря |
| Возрастающий/убывающий порядок ключей | Поведение на упорядоченном вводе |
| Слова разной длины и длинные общие префиксы | Влияние строковых сравнений и хранения |
| Save и Load отдельно | Файловый формат, сериализация и восстановление |
| Load при большом старом словаре | Пик одновременного хранения старого и нового дерева |

Сравнить несколько степеней, например 2, 8, 16, 32 и 64. Это экспериментальные значения, а не заранее оптимальные параметры. Слишком малый `t` увеличивает высоту и число узлов; слишком большой увеличивает объём сдвигов и резерв памяти.

Для каждого запуска фиксировать число команд, максимальный/конечный размер словаря, распределение длин, долю успешных запросов и seed. Генерация входа не должна случайно входить в измерение только одной версии.

Повторять измерения несколько раз, например 5, сравнивать медиану и разброс. Условия должны совпадать: машина, ОС/WSL, компилятор, флаги, вход, режим вывода. Для файловых сценариев учитывать кэш файловой системы и явно описать, как проводились повторные запуски.

`std::map` полезен для сравнения, но нельзя автоматически объявлять B-дерево быстрее по одной асимптотике: влияют строки, контейнеры и распределение команд. Сравнивать либо одинаковые оболочки ввода-вывода, либо прямые вызовы обоих контейнеров.

## 10. Материалы для отчёта

Сразу сохранять дневник и сырые результаты. Не восстанавливать историю задним числом и не придумывать найденные ошибки.

| Дата и этап | Действия | Средство | Фактический результат | Следующий шаг |
| --- | --- | --- | --- | --- |
| Заполнить при выполнении | Например, проверка удаления | Валидатор, случайные тесты | Указать результат/воспроизводимый сбой | Указать исправление или следующую проверку |

Перед исправлением сохранить воспроизводимый тест, версию исходников и диагностический вывод. После исправления повторить тот же тест и подходящие проверки. Для оптимизации — убедиться, что поведение не изменилось, затем сравнить скорость и память на одинаковой нагрузке.

| Версия | Нагрузка | Время, медиана | Пик RSS | Ошибки памяти | Изменение |
| --- | --- | --- | --- | --- | --- |
| Базовая | Указать параметры | Измерить | Измерить | Указать результат | Исходная рабочая реализация |
| Исправленная | Те же параметры | Измерить | Измерить | Указать результат | Конкретное исправление |

Ускорение при сопоставимых условиях: `T_before / T_after`. Уменьшение времени в процентах: `(T_before - T_after) / T_before * 100%`. Изменение памяти анализировать отдельно: ускорение может сопровождаться ростом RAM.

Если ошибок не найдено, написать, что именно проверялось и какой результат получен. Если обнаружен только узкий участок производительности, исследовать его. Не нужно намеренно оставлять дефект ради раздела «исправления». При сравнении версий с разной корректностью обязательно отметить это различие: быстрый неправильный ответ не является лучшим результатом алгоритма.

Каркас отчёта:

1. Постановка задачи и выбранное B-дерево.
2. Инварианты, интерфейс и оценки сложности.
3. Дневник действий и использованные средства.
4. Методика тестирования и параметры нагрузок.
5. Найденные недочёты с воспроизводимыми примерами и диагностикой.
6. Исправления и проверка после них.
7. Сравнение версий по времени и памяти.
8. Выводы о причинах результатов и полученном опыте.
9. Источники и при необходимости приложения с логами.

[Предложенный в условии шаблон](https://github.com/toshunster/MAI-da/tree/master/report_pattern) использует LaTeX и отдельные части для постановки, кода, исследования, выводов и литературы. Его оформление можно использовать, но содержательные требования задаются самим заданием G.

## 11. Проверка готовности

- Все обязательные ответы имеют точный регистр и формат.
- Работают слово длиной 256, значение 0 и `2^64 - 1`.
- Пройдены все ветви удаления и изменения корня.
- Проверки инвариантов и сравнение с эталоном не находят расхождений.
- Успешный Load заменяет словарь, ошибочный — сохраняет прежний.
- Отсутствующий и нулевой файл при Load дают `OK` и пустой словарь.
- Ошибки открытия, чтения, записи и выделения памяти обрабатываются согласованно.
